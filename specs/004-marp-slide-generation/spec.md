# Feature Specification: Marp-Based Slide Generation for Major Repo Changes

**Feature Branch**: `feature/48-marp-slide-generation`

**Created**: 2026-09-15

**Status**: Draft

> **Source**: [#48](https://github.com/jackmurphyslalom/yugastore-java/issues/48) — linked on 2026-09-15

**Input**: User description: "Title: Add Marp-based slide generation for major repo changes. Summary: Adopt Marp (https://marp.app/) to generate slide decks summarizing major changes made to this repo, for later presentation (e.g. demos, retros, stakeholder updates). Motivation: We regularly make significant architectural/feature changes (see docs/decisions/, specs/) but have no lightweight way to turn that history into a presentable slide deck. Marp supports Markdown-to-slides, which fits our existing Markdown-heavy docs workflow. Proposed Scope: Add Marp CLI usage via npx (no new package.json / Node dependency footprint — this is a Java/Maven repo) to the repo/toolchain, documented. Define a convention/location for slide decks: docs/slides/. Establish a lightweight process/skill for converting a decision, ADR, or spec summary into a Marp deck. Optionally wire a script/task to export decks to PDF/HTML for sharing. Out of Scope: Automated generation of slides directly from git history/diffs (future enhancement) — the sample deck content itself is authored/curated by hand, not auto-generated by tooling. Acceptance Criteria: Marp tooling is installed/documented (npx-based CLI usage; no VS Code extension requirement). A sample deck exists demonstrating real recent changes from this repo — specifically covering all major PRs merged since PR #1 (the AI-SDLC bootstrap), i.e. PRs #1 through #52 merged 2026-09-14 through 2026-09-15, including: AI-SDLC bootstrap, requirements transcripts, context bootstrap docs, project constitution ratification, gh-agent-board tooling, writing style guide, MCP config, Context7 instructions, Brewfile dev setup, GitHub Issues/Spec Kit boundary docs, CI/CD bootstrap, CI stabilization, and the standardized Java testing framework alignment (JUnit 5 + Mockito + AssertJ + JaCoCo). Docs explain how to author and export a new deck (docs/slides/README.md or similar)."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Author a deck summarizing a completed change (Priority: P1)

A team member who just finished a significant architectural or feature change (a decision, ADR, or spec) wants to turn that work into a short slide deck for a demo, retro, or stakeholder update, without learning a new tool from scratch.

**Why this priority**: This is the core value of the feature — turning existing Markdown-heavy history into something presentable. Without this, nothing else in the feature matters.

**Independent Test**: Can be fully tested by taking an existing decision/spec document, writing a new Markdown deck under `docs/slides/` following the documented convention, and rendering it to a viewable slide deck using only the documented `npx` command.

**Acceptance Scenarios**:

1. **Given** a completed decision or spec document, **When** the author writes a Marp-formatted Markdown file in `docs/slides/`, **Then** running the documented `npx` command renders it as a slide deck.
2. **Given** the author has no prior Marp experience, **When** they follow `docs/slides/README.md`, **Then** they can produce a valid deck without asking a teammate for help.

---

### User Story 2 - Reviewer browses the sample deck covering recent repo history (Priority: P2)

A reviewer or stakeholder who was not closely involved in recent work wants a single deck that summarizes the major changes made to the repo since the AI-SDLC bootstrap, so they can catch up without reading every decision and spec individually.

**Why this priority**: Demonstrates the feature's value with real content and gives the team a working example to copy for future decks; also directly satisfies the issue's acceptance criteria.

**Independent Test**: Can be fully tested by opening the sample deck and confirming it contains a distinct, identifiable slide or section for each of the major merged-PR themes listed in scope, without needing to cross-reference git history to understand any of them.

**Acceptance Scenarios**:

1. **Given** the sample deck in `docs/slides/`, **When** a reviewer reads it top to bottom, **Then** every listed major-change theme (AI-SDLC bootstrap, requirements transcripts, context bootstrap docs, project constitution ratification, gh-agent-board tooling, writing style guide, MCP config, Context7 instructions, Brewfile dev setup, GitHub Issues/Spec Kit boundary docs, CI/CD bootstrap, CI stabilization, Java testing framework alignment) appears as its own slide or clearly labeled section.
2. **Given** the sample deck source Markdown, **When** it is rendered with the documented `npx` command, **Then** it produces a viewable deck without errors.

---

### User Story 3 - Share a deck as PDF/HTML with people who don't use Marp (Priority: P3)

A presenter needs to send a deck to stakeholders who won't run any tooling themselves, so they export the deck to a static PDF or HTML file to attach to an email or upload to a shared drive.

**Why this priority**: Useful for real-world sharing but not required to prove the core authoring workflow works; the feature is still valuable without it if authors can present directly from rendered Markdown.

**Independent Test**: Can be fully tested by running the documented export command/script against an existing deck and confirming a PDF and/or HTML file is produced.

**Acceptance Scenarios**:

1. **Given** an existing deck Markdown file, **When** the author runs the documented export command, **Then** a PDF and/or HTML file is produced alongside the source.

---

### Edge Cases

- What happens when a contributor's machine has Node.js/npx available but has never run Marp CLI before? The documented command must work on first invocation (npx fetches the package on demand) without any additional repo-level setup.
- How does the process handle a deck author who wants to cover a change not on the current sample-deck list? The documented convention must generalize beyond the sample deck's specific topics — it is not limited to the initial 12 themes.
- What happens if the underlying decision/spec content referenced by a deck changes after the deck is authored? Decks are treated as a point-in-time snapshot; keeping them in sync with later doc changes is a manual authoring responsibility, not automated.
- What happens if someone expects slides to be generated automatically from git history or diffs? This is explicitly out of scope; docs must state that deck content is hand-authored/curated.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Docs MUST explain how to render a Marp Markdown deck using the `npx` command-line invocation, without requiring any new Node.js dependency to be added to this repo's `package.json`/build (this is a Java/Maven repo) and without requiring a VS Code extension.
- **FR-002**: The repo MUST designate `docs/slides/` as the canonical location for Marp slide deck source Markdown files.
- **FR-003**: Docs MUST describe the authoring convention for a deck (e.g., Marp front matter, per-slide separators, recommended structure for turning a decision/ADR/spec into slides).
- **FR-004**: The repo MUST include a sample deck under `docs/slides/` that summarizes real, already-merged major changes to this repo, covering (at minimum, one slide or clearly labeled section each) all of: AI-SDLC bootstrap, requirements transcripts, context bootstrap docs, project constitution ratification, gh-agent-board tooling, writing style guide, MCP config, Context7 instructions, Brewfile dev setup, GitHub Issues/Spec Kit boundary docs, CI/CD bootstrap, CI stabilization, and Java testing framework alignment (JUnit 5 + Mockito + AssertJ + JaCoCo).
- **FR-005**: Docs MUST state explicitly that deck content (including the sample deck) is authored/curated by hand and that automatically generating slides from git history or diffs is out of scope.
- **FR-006**: Docs MUST explain how to export a deck to PDF and/or HTML for sharing with people who do not run Marp tooling themselves, via a documented command or a lightweight repo script/task.
- **FR-007**: Documentation covering this feature MUST live in `docs/slides/README.md` (or an equivalently discoverable location under `docs/slides/`) and MUST be reachable by a new contributor without prior knowledge of Marp.

### Key Entities

- **Slide Deck**: A Marp-formatted Markdown file stored under `docs/slides/`, representing a presentable, hand-curated summary of one or more decisions, ADRs, specs, or a period of repo history. Rendered on demand via `npx`; not committed as a pre-rendered binary artifact.
- **Deck Export**: A PDF or HTML file generated from a Slide Deck's Markdown source, used to share the deck with people who do not run Marp tooling directly. Treated as a derived, regenerable artifact rather than a source of truth.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A team member with no prior Marp experience can render a new deck from a Markdown file to a viewable slide deck in under 5 minutes using only the documented `npx` command.
- **SC-002**: A reviewer can read the sample deck and correctly identify all 12 listed major-change themes without consulting git history, decisions, or specs directly.
- **SC-003**: A team member can export any deck in `docs/slides/` to a shareable PDF or HTML file using only documented commands, with no manual troubleshooting.

## Assumptions

- Node.js (and therefore `npx`) is already available on contributor machines; this feature does not require adding Node.js as a project prerequisite beyond what's needed to run `npx` commands ad hoc.
- The Marp CLI (`@marp-team/marp-cli`) is invoked via `npx` on demand each time rather than vendored or added as a pinned dependency in this Java/Maven repo.
- "PRs #1 through #52 merged 2026-09-14 through 2026-09-15" and the 12 named themes in the acceptance criteria are the authoritative source list for the sample deck's content; the deck does not need to enumerate every individual PR by number as long as each named theme is represented.
- Supported export formats are PDF and HTML (Marp's standard built-in export targets); other formats (e.g., PPTX, images) are not required.
- No CI automation is required to regenerate or validate decks on every commit; decks are authored and exported manually as needed.
- [Dependency on existing system/service, e.g., "Requires access to the existing user profile API"]
